Proposal for leadership review

Restrict access to Finance and Operations environments

Today, anyone in the organization with a Dynamics 365 or Power Platform license is automatically added to our Finance and Operations environments, including production. This proposal closes that gap with Microsoft Entra security groups, in six steps over about four weeks, at no additional licensing cost.

Recommendation

Approve a phased rollout of security groups: a pilot on two test environments, then the remaining test environments, then production in a scheduled window. Every new environment created in the move from Lifecycle Services to the unified platform gets its group on day one.

Why this matters

The risk today

  • Without a security group, every licensed user in the tenant is added to the environment's data platform (Dataverse). That includes people who only have a Sales, Power Apps, or Power Automate license and have no business in finance or supply chain data.
  • The Power Platform admin center flags this for 13 of our Finance and Operations environments, including production.
  • Access is granted by default and has to be taken away, which is the reverse of least-privilege practice and hard to show in an audit.

What changes

  • Only named members of an approved group can be users in each environment. Adding or removing someone from the group grants or removes access.
  • Access becomes auditable in one place, Microsoft Entra, and fits existing joiner, mover, and leaver processes.
  • Security roles inside Finance and Operations are unchanged. This controls who can get in, not what they can do once inside.
  • Integrations that use application registrations are unaffected. So are Power Platform and Global Administrators.

The main risk of the change itself

When a group is attached to an environment that already has users, everyone who isn't in the group loses access immediately. That includes user accounts that own automated flows and integrations. The plan below is built around preventing that: build the member list first, prove it on test environments, and keep a rollback ready.

The plan

Design the groups

Week 1 · Platform admin

Start with two groups: SG-D365FO-Prod for production and SG-D365FO-NonProd for test and development environments. Optionally add SG-D365FO-UAT if business testers should reach acceptance testing without seeing development environments.

  • Add members directly. Members of groups nested inside the environment group aren't added automatically.
  • For production, consider an Entra dynamic group based on the Finance or Supply Chain license, if Entra ID P1 is available. It keeps up with new hires without manual work.

Done when: group names, scope, and membership rules are agreed.

Build the member list

Week 1 · Platform admin, functional leads

For each environment, list everyone who needs access, starting from the users who are active there today.

  • People who use Finance and Operations or customer engagement features.
  • User accounts that own automated flows or connections. If they're left out, those automations stop, including the "Client Data Export Processor" flow in production.
  • Service accounts that are ordinary user accounts, Dynamics 365 Administrators, partner and consultant accounts, and testers.

Done when: functional leads have signed off the list for each environment.

Create the groups

Week 2 · Identity team

Create the groups in Microsoft Entra (or the Microsoft 365 admin center) and load the approved members. This needs the Groups Administrator or User Administrator role, so the identity team does this step. Groups must be cloud security groups or Microsoft 365 groups; groups synced from on-premises Active Directory aren't supported.

Done when: groups exist and their membership matches the signed-off lists.

Pilot on two test environments

Week 2 · Platform admin, testers

Attach the non-production group to one unified environment (LVS-FO-USE-SUPPORT-01) and one Lifecycle Services environment (lvs-fo-testing-01), since the two types behave differently. Then confirm:

  • Members can sign in and work normally, and non-members are blocked. This includes checking whether the Finance and Operations web client itself is blocked, which Microsoft's documentation doesn't make clear.
  • Dual-write, virtual entities, flows, and integrations keep running.
  • How long a newly added member waits for access, and how long rollback takes.

Done when: every check passes and the results are written up.

Roll out to the remaining environments

Weeks 3–4 · Platform admin

Apply the non-production group to the remaining active test environments in week 3. Apply the production group to LVS-FO-PROD in week 4, in a quiet window with users told in advance.

  • After each change, compare the users who lost access with what the list predicted.
  • Set a governance contact, so anyone blocked sees who to ask instead of a dead end.

Done when: production is restricted, with no unplanned loss of access or broken automation.

Build it into the migration

Ongoing · Platform admin

Every new unified environment gets its security group when it's created, so it never goes through the disable-everyone step. Test environments due for retirement in the move from Lifecycle Services aren't worth retrofitting. The effort goes to production and to environments that will stay.

Done when: assigning a group is a standard part of the environment request and provisioning checklist.

Decisions requested

  1. Approve the phased plan and the four-week timeline.
  2. Confirm the group design: two groups, or three with a separate acceptance-testing group.
  3. Name owners: an identity team contact and a functional lead for each area to sign off the member list.
  4. Agree the production change window for week 4.
  5. Make security groups mandatory for every new environment created in the move to the unified platform.
